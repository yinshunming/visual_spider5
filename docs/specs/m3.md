# M3 Spec: 单页运行、结果与导出

> Spec 草稿；review 通过后再发到 GitHub issue tracker（`ready-for-agent`, `m3`）。
> 与 [`product-spec.md`](../product-spec.md)、[`architecture.md`](../architecture.md)、[`roadmap.md`](../roadmap.md) §7、[`docs/adr/0003-organize-code-by-business-module.md`](../adr/0003-organize-code-by-business-module.md)、[`docs/adr/0004-config-and-run-lane-pools-are-independent.md`](../adr/0004-config-and-run-lane-pools-are-independent.md)、[`docs/adr/0005-task-readiness-is-syntax-only.md`](../adr/0005-task-readiness-is-syntax-only.md)、[`docs/adr/0006-run-concurrency-and-scheduling.md`](../adr/0006-run-concurrency-and-scheduling.md) 配套。
> 上游约束：M2 已落地的 `extraction.ExtractionPreview` / `visualbrowser.TargetUrlPolicy` / `visualbrowser.ConfigLanePool` / `task.TaskReadiness`（`m2.md` 退出标准已通过）；M1 的 `identity` / `task` / `shared` 三模块稳定；Flyway V1（`app_user` / `collection_task` / `system_setting`）已上线。

## Problem Statement

M2 让采集人员能可视化配置单页任务并预览，但**不能真正跑**：`task.TaskSnapshotFactory` 仍是占位（抛 `UnsupportedOperationException("M3 启用")`），没有 `collection_run` / `run_result` / `run_event` 表，没有运行调度、取消、中断恢复，没有结果分页与导出。M3 要把这条纵向切片打通：单页任务从配置 -> 运行 -> 结果 -> 下载。

如果不把 M3 收敛清楚，会同时出现两类风险：

- **跨里程碑堆叠**：运行/结果这套机器是按完整列表 + 多页愿景设计的（7 态状态机、批量 sink、去重列、停止原因枚举）。若不明确"宽接口窄实现"边界，要么把 M4/M5 的列表/翻页/去重逻辑提前混进 M3（违反 roadmap §7 不做项），要么把 schema/enum 建得过窄导致 M4/M5 反复迁移。
- **M2 契约的潜伏隐患**：`FieldDefinition` 没有 `selectorType`，`DomState.querySelectorAll` 是 CSS-only（`document.querySelectorAll`），而 M2 编辑器/候选生成已支持 XPath。XPath 字段选择器校验通过、但预览与运行会报 `SELECTOR_SYNTAX_INVALID`。M3 运行要 honor 保存的选择器，必须正面修掉。

M3 也是 `run` 与 `result` 两个模块第一次落地稳定 `spi/`：`RunCoordinator` / `RunRecovery` / `RunResultSink` / `RunResultQuery` / `RunExport` / `RetentionCleanup` 都在 M3 从占位 `package-info` 升级为真实实现。

## Solution

把 M3 落地为 7 张 issue，按依赖顺序推进（a -> b -> (c ∥ d) -> e -> f -> g）：

- **(a) 快照 + schema + 状态机契约**：`TaskSnapshotFactory` 真实实现（不可变快照 + version 校验）；V2 migration 建 `collection_run` / `run_result` / `run_event` 三表 + 索引 + 级联；`TaskDefinition` 扩展 `waitPolicy`（`extraWaitSeconds` 0–5，默认 0）与 `FieldDefinition.selectorType`（CSS/XPATH，默认 CSS），`schemaVersion` 保持 1；`DomState` 类型感知（修 M2 XPath 隐患，预览与运行共用）；`run` 状态枚举（7 态）与 `stopReason` 枚举（前向兼容全集）常量定义。
- **(b) 运行调度 + RunLanePool + 并发 + 中断恢复**：`RunLanePool`（镜像 `ConfigLanePool`，3 lane，ADR-0004）；`RunCoordinator`（start / cancel / get / list / progress）；并发执行（ADR-0006：每用户 (WAITING+RUNNING)≤1 拒 `USER_RUN_LIMIT`，全局 RUNNING≤3 由 RunLanePool 物理限，WAITING 队列 = PG `status=WAITING` 记录，单 JVM 派发器 lane 释放时取最旧）；`RunRecovery` 启动扫描把残留 WAITING/RUNNING 标记 INTERRUPTED。
- **(c) 单页执行引擎**：`SinglePageRunExecutor`（导航 -> `DOMContentLoaded` -> 字段选择器等待 15s -> `extraWaitSeconds` -> 用运行 lane Page 构造 `DomState` -> `ExtractionPreview.preview` -> `RunResultSink.appendBatch` 写 1 条结果 + 事件）；页面失败重试 2 次（共 3 次）；取消协作式信号在每个检查点查验；Playwright 超时兜底释放 lane。
- **(d) 结果查询 + 流式导出 + 保留清理**：`RunResultQuery` 按 `(run_id, sequence_no)` keyset 分页 + 汇总统计；`RunExport` CSV/JSON 直接写 `HttpServletResponse` OutputStream，游标每批 ~1000 行，10k 行不全量加载；`RetentionCleanup` `@Scheduled` 每日按 `finished_at` 删 30 天前 run，FK 级联删 result/event。
- **(e) 进度 WebSocket + REST API**：`/ws/runs/{runId}`（握手校验 JSESSIONID + CSRF + run 所有权，admin 可访问任意 run，复用 M2 拦截器模式）；服务端在状态变更/批次边界推结构化进度，客户端仅发 `cancel`；`/api/runs/**` REST（start/list/get/cancel/results/export/snapshot/events）。
- **(f) 前端运行列表 + 详情**：Vue 运行列表（REST 轮询）+ 运行详情（WS 进度 / 快照查看 / 分页结果表 / 取消 / CSV·JSON 导出），**无实时画面**；`@visualspider/contracts` 增加 `run.ts` REST DTO + `runWsProtocol.ts` WS schema。
- **(g) E2E smoke + 10k 导出 fixture**：`scripts/e2e/m3-smoke.ps1` / `m3-smoke.sh` 全链路；10k 结果流式导出测试；Linux smoke 写明 not executed（延后 M7）。

(a) 是契约与 schema（跨 task/extraction/run，seam = 快照与提取契约，migration 与 run 模块首批消费同 issue）；(b)(c) 是 `run` 模块核心；(d) 是 `result` 模块；(e) 是 `run`+`result` 的 api 层；(f) 前端；(g) 端到端。M3 不引入 Docker / Redis / Testcontainers / 任何新外部依赖；不实现列表、翻页、内容页、去重、跨运行增量、完整 SSRF、定时调度。

## User Stories

1. As a **首版采集人员**，I want **把一个可运行（READY）单页任务一键启动**，so that **我不需要打开配置会话就能跑出结果**。
2. As a **首版采集人员**，I want **运行开始后看到状态、阶段、当前 URL、计数和耗时**，so that **我能判断它在正常推进而不是卡住**。
3. As a **首版采集人员**，I want **运行期间编辑原任务不影响这次运行**，so that **我看到的结果对应运行开始时固化的任务定义，不会被我的后续改动污染**。
4. As a **首版采集人员**，I want **页面超时或失败时自动重试，最终失败有明确原因**，so that **偶发网络抖动不会让整次运行白跑，真失败时我知道为什么**。
5. As a **首版采集人员**，I want **随时能取消运行，取消后浏览器很快释放**，so that **我点错或改主意时不会占用 lane 到 30 分钟**。
6. As a **首版采集人员**，I want **运行结果分页查看并流式下载 CSV/JSON**，so that **我能拿到数据而不卡死浏览器，也不会因为结果多而 OOM**。
7. As a **首版采集人员**，I want **应用崩溃重启后，遗留运行显示为已中断、已写结果仍可导出**，so that **我不会面对一个永远“运行中”的僵尸运行，也不丢已采集的数据**。
8. As a **首版采集人员**，I want **用 XPath 选的字段在运行时也能取到值**，so that **我在配置时验证过的规则在运行时一致生效**。
9. As a **首版管理员**，I want **能看到和处理全部用户的运行与结果**，so that **我能协助排查问题，不被所有权挡在外面**。
10. As a **首版管理员**，I want **第二个应用实例连同一业务库时不进入运行调度**，so that **不会两个 JVM 重复消费同一个运行**（M3 仅声明单实例 + 启动恢复，跨实例租约 M6）。
11. As a **M4 接手人**，I want **M3 的 `collection_run` 状态枚举、`stopReason`、`run_result.unique_key_hash`、批量 sink 接口已经前向兼容**，so that **M4 加列表/去重时不改 schema、不迁移、不破接口**。
12. As a **M6 接手人**，I want **M3 的容量与保留是常量、运行入口复用 `TargetUrlPolicy`**，so that **M6 把常量写入 `system_setting`、把 `BasicTargetUrlPolicy` 替换为完整 SSRF 时只换实现不改调用点**。
13. As a **首版审计员**，I want **M3 的技术日志不含页面内容、结果字段值、Cookie 或密码**，so that **M1/M2 的日志脱敏正则继续覆盖 run/result 路径**。

## Implementation Decisions

### D1. `run` 模块结构

```
com.visualspider.run
├── spi/                         # 公开 stable interface (ADR-0003 seam)
│   ├── RunCoordinator.java          # start/cancel/get/list/progress
│   ├── RunRecovery.java             # 启动恢复扫描
│   ├── RunState.java                # 状态枚举 (7 态)
│   ├── StopReason.java              # 停止原因枚举 (前向兼容全集)
│   ├── RunSummary.java              # 列表/概览 record
│   └── RunDetail.java               # 详情 record (含快照元数据)
├── internal/                    # 实现, 包级私有
│   ├── RunLanePool.java             # 镜像 ConfigLanePool, 3 lane (ADR-0004)
│   ├── RunCoordinatorImpl.java      # 创建/取消/查询 + 并发检查
│   ├── RunDispatcher.java           # 单 JVM 派发器: WAITING -> lane
│   ├── SinglePageRunExecutor.java   # 单页执行 (导航/等待/提取/重试/取消)
│   ├── RunExecutionContext.java     # 运行内 volatile 取消标志 + 计数
│   ├── JdbcRunRepository.java       # collection_run 访问
│   └── RunOwnerHandshakeInterceptor.java  # /ws/runs/{runId} 握手
└── api/                         # REST + WebSocket 入口
    └── RunController.java           # /api/runs/** + WS handler 注册
```

迁移/升级原则（与 M2 一致）：

- `run` 模块 M0.5 仅 `package-info.java`；M3 首次落地稳定 `spi/`，`internal/` 包级私有不跨模块引用。
- `result` 模块同样从 `package-info` 升级到 `spi/`（见 D12）。
- 不修改 M2 `visualbrowser` 模块 interface 形状；运行 lane 复用 M0 `BrowserLane`，与配置 lane 同构但独立池（ADR-0004）。
- `@Disabled` 仅允许 M0 spike 已有的 `ScreencastFrameProducerIT`；M3 不新增任何 `@Disabled`。

### D2. `RunCoordinator` interface 草案

```java
public interface RunCoordinator {
    /** 从 READY 任务创建运行（WAITING）；同事务生成快照 + 并发检查。 */
    RunSummary start(long taskId, ActorId actor);
    /** 协作式取消；终态运行不可取消。 */
    void cancel(long runId, ActorId actor);
    /** 详情：状态/计数/阶段/当前URL/快照元数据。 */
    RunDetail get(long runId, ActorId actor);
    /** 分页列表（owner 范围；admin 全局）。 */
    Page<RunSummary> list(ActorId actor, RunFilter filter);
    /** WS 握手后下发当前进度快照。 */
    RunProgress progress(long runId, ActorId actor);
}
```

- `start` 校验：身份、任务所有权、`status == READY`（否则 `TASK_NOT_READY`）；同事务内 `SELECT count(*) WHERE owner_id=? AND status IN ('WAITING','RUNNING')` ≥ 1 -> `USER_RUN_LIMIT`；生成 `TaskSnapshot` + 插入 `WAITING` run 记录。
- `start` 的计数检查 + 插入用 in-JVM 锁串行（单实例足够；跨实例租约 M6），消除两个并发请求同时通过计数检查的竞态。
- 所有查询带 `owner_id`（admin 全局），与 `task` 模块同模式；不依赖前端隐藏。

### D3. `RunLanePool`（镜像 `ConfigLanePool`）

```java
public final class RunLanePool implements LanePool, AutoCloseable {
    public static final int DEFAULT_CAPACITY = 3;  // ADR-0004
    // 结构与 ConfigLanePool 同: 固定 3 BrowserLane, Semaphore, available 列表
}
```

- 启动时 `ApplicationRunner` 初始化 3 个 `BrowserLane`（各自独立 Playwright + Browser），单例。
- 与 `ConfigLanePool` 互不感知（ADR-0004）；两池独立，配置会话与运行不争抢 lane。
- **关键差异**：配置会话 `acquire` 池满抛 `CONFIG_LANE_FULL`（拒绝，因为配置会话不排队）；运行 `acquire` **永不抛满**——`RunDispatcher` 只在 `borrowedCount() < capacity()` 时才派发一个 WAITING run，拿到再 `acquire`。排队发生在 PG 的 WAITING 记录，不在 lane 池。
- 每次运行新建独立、非持久化 `BrowserContext`（architecture §4.2）；运行结束按 `Page -> BrowserContext -> Browser/Playwright` 顺序在同一线程回收（spike §4.1）。
- 容量常量 `DEFAULT_CAPACITY = 3` 写死；配置化延后 M6（与 ADR-0004 同先例）。

### D4. `TaskSnapshotFactory` M3 实现 + 快照存储

替换 `UnsupportedTaskSnapshotFactory`：

```java
@Service
public final class JdbcTaskSnapshotFactory implements TaskSnapshotFactory {
    public TaskSnapshot snapshot(long taskId, ActorId actor) {
        // 1. 读 collection_task (带 owner 校验)
        // 2. 构造 TaskSnapshot(taskId, ownerId, name, mode, schemaVersion, version, definition)
        //    definition 是当前 TaskDefinition 的深拷贝 (record 不可变, 直接引用即可)
        // 3. 不写库; 由 RunCoordinator.start 在同事务把 snapshot 序列化为 JSONB 存入 collection_run.snapshot
    }
}
```

- 快照内容 = 完整 `TaskDefinition`（含 M3 新增的 `waitPolicy` + 字段的 `selectorType`）+ `taskId/ownerId/name/mode/schemaVersion/version`。
- `collection_run.snapshot` JSONB 不可修改（运行创建后只读）；运行详情页可查看当时快照（roadmap §7 退出标准）。
- `@JsonIgnoreProperties(ignoreUnknown = true)`（已存在于 `TaskDefinition` / `FieldDefinition`）保证历史快照可解释（architecture §11 风险表“只前滚兼容”）。
- 运行期间编辑原任务只改 `collection_task`，不动 `collection_run.snapshot`；当前/历史运行不受影响。

### D5. V2 migration（三表 + 索引 + 级联）

```sql
-- V2__run_result_event.sql
-- M3: collection_run / run_result / run_event 三表 + 索引 + 级联
-- 历史数据: 全新表, 无历史数据迁移
-- 锁影响: 全新表 CREATE, 不锁既有表; 索引建立无数据
-- 回滚: 无 (只前滚兼容; 回滚需 drop 三表, 会丢运行历史)

CREATE TABLE collection_run (
    id                BIGSERIAL PRIMARY KEY,
    task_id           BIGINT       NOT NULL REFERENCES collection_task(id),
    owner_id          BIGINT       NOT NULL REFERENCES app_user(id),
    snapshot          JSONB        NOT NULL,
    status            VARCHAR(16)  NOT NULL CHECK (status IN
                        ('WAITING','RUNNING','SUCCESS','PARTIAL_SUCCESS',
                         'FAILED','CANCELLED','INTERRUPTED')),
    stop_reason       VARCHAR(32),
    cancel_requested  BOOLEAN      NOT NULL DEFAULT false,
    page_count        INT          NOT NULL DEFAULT 0,
    record_count_raw      INT      NOT NULL DEFAULT 0,
    record_count_dedup    INT      NOT NULL DEFAULT 0,
    record_count_final    INT      NOT NULL DEFAULT 0,
    fail_count        INT          NOT NULL DEFAULT 0,
    current_url       TEXT,
    stage             VARCHAR(32),
    started_at        TIMESTAMPTZ,
    finished_at       TIMESTAMPTZ,
    created_at        TIMESTAMPTZ  NOT NULL DEFAULT now()
);
COMMENT ON TABLE collection_run IS '采集运行权威状态; snapshot 不可修改; status 7 态 (M3 产 6 态, PARTIAL_SUCCESS 留位 M4)';
COMMENT ON COLUMN collection_run.stop_reason IS '停止原因; WAITING/RUNNING 阶段为 NULL';

CREATE INDEX idx_collection_run_owner_status_created
    ON collection_run (owner_id, status, created_at DESC);
CREATE INDEX idx_collection_run_finished
    ON collection_run (finished_at)
    WHERE finished_at IS NOT NULL;  -- 保留清理用

CREATE TABLE run_result (
    id              BIGSERIAL PRIMARY KEY,
    run_id          BIGINT       NOT NULL REFERENCES collection_run(id) ON DELETE CASCADE,
    sequence_no     INT          NOT NULL,
    unique_key_hash BYTEA,       -- M3 恒 NULL; M4 去重启用
    data            JSONB        NOT NULL,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    UNIQUE (run_id, sequence_no)
);
COMMENT ON TABLE run_result IS '结果行; 按 (run_id, sequence_no) 分页/游标; run 删除级联';

CREATE INDEX idx_run_result_run_seq ON run_result (run_id, sequence_no);

CREATE TABLE run_event (
    id           BIGSERIAL PRIMARY KEY,
    run_id       BIGINT       NOT NULL REFERENCES collection_run(id) ON DELETE CASCADE,
    level        VARCHAR(16)  NOT NULL CHECK (level IN ('INFO','WARN','ERROR')),
    stage        VARCHAR(32),
    url          TEXT,
    error_code   VARCHAR(64),
    message      TEXT         NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);
COMMENT ON TABLE run_event IS '用户可见结构化事件; 不复制完整技术堆栈';

CREATE INDEX idx_run_event_run_created ON run_event (run_id, created_at);
```

migration 说明（AGENTS 要求）：全新表，无历史数据；CREATE 不锁既有表；只前滚兼容，回滚 = drop 三表（会丢运行历史，故不提供回滚脚本，靠数据库备份恢复）。

### D6. `TaskDefinition` 扩展（`schemaVersion` 保持 1）

```java
public record TaskDefinition(
        int schemaVersion,
        TaskMode mode,
        String startUrl,
        Viewport viewport,
        WaitPolicy waitPolicy,        // M3 新增; 可空 -> 默认 extraWaitSeconds=0
        List<FieldDefinition> fields) {

    public TaskDefinition {
        if (fields == null) fields = List.of();
        if (waitPolicy == null) waitPolicy = new WaitPolicy(0);
    }
}

public record WaitPolicy(int extraWaitSeconds) {
    public WaitPolicy {
        if (extraWaitSeconds < 0 || extraWaitSeconds > 5)
            throw new IllegalArgumentException("extraWaitSeconds 必须 0-5");
    }
}

public record FieldDefinition(
        String name,
        FieldSource source,
        String selector,
        SelectorType selectorType,   // M3 新增; 可空 -> 默认 CSS
        String attributeName,
        ResultType resultType,
        TrimPolicy trim,
        String regex,
        boolean required) {}

public enum SelectorType { CSS, XPATH }
```

- 两处都是**加可选字段 + 默认值**：旧快照（M2 保存的）反序列化时 `waitPolicy` 为 null -> compact 构造器填默认 `WaitPolicy(0)`；`selectorType` 为 null -> 默认 `CSS`。语义与 M2 行为一致（M2 不存在额外等待、字段选择器实际按 CSS 跑）。
- **不 bump `schemaVersion`**：加字段、`@JsonIgnoreProperties` 保证旧 reader 可读新快照、新 reader 可读旧快照，非破坏性（architecture §11“只前滚兼容”）。
- `TaskReadiness.validateForRun`（M2 实现）扩展：`extraWaitSeconds` 范围 0–5 校验（失败 `TASK_INVALID_WAIT_POLICY`）；`selectorType` 非 null 时在 `CSS`/`XPATH` 取值内。`PAGE_URL` 字段 `selectorType` 忽略（与 selector 同）。

### D7. `DomState` 类型感知（修 M2 XPath 隐患）

`extraction.spi.ExtractionPreview.DomState` 扩展（加法，保留旧方法）：

```java
interface DomState {
    String url();
    /** CSS 查询（保留 M2 签名，默认委托 query）。 */
    default List<Node> querySelectorAll(String css) { return query(css, SelectorType.CSS); }
    /** M3 新增：按类型查询，CSS 走 document.querySelectorAll，XPath 走 document.evaluate。 */
    List<Node> query(String selector, SelectorType type);
}
```

- `ExtractionPreviewImpl.readRaw` 改为 `domState.query(field.selector(), field.selectorType())`，按 `selectorType` 分发。
- `VisualSession.preview`（M2 配置预览）与 `SinglePageRunExecutor`（M3 运行）都构造实现 `query` 的 `DomState`：CSS 走 `document.querySelectorAll`，XPath 走 `document.evaluate`（与 `PlaywrightControl.validateSelector` 同一段 JS，抽公共 helper）。
- **顺带修 M2 preview 的 XPath 隐患**：M2 保存的 XPath 字段在预览时不再误报 `SELECTOR_SYNTAX_INVALID`。该修复随 (a) 契约 ticket 落地，`ExtractionPreviewImplTest` 增加 XPath 用例。
- `SelectorType` 由 `task.domain` 定义（`FieldDefinition` 持有），`extraction` 模块 import；不反向依赖。

### D8. 并发执行与调度（ADR-0006）

详见 [`docs/adr/0006-run-concurrency-and-scheduling.md`](../adr/0006-run-concurrency-and-scheduling.md)。要点：

- **创建（`RunCoordinator.start`）**：in-JVM 锁内，同事务做 `SELECT count(*) WHERE owner_id=? AND status IN ('WAITING','RUNNING')` ≥ 1 -> 拒 `USER_RUN_LIMIT`（409）；通过则生成快照 + 插入 `WAITING` run 记录。
- **每用户 (WAITING+RUNNING) ≤ 1**：第 2 个直接拒，队列自然有界（≤ 账号数个等待）。
- **全局 RUNNING ≤ 3**：由 `RunLanePool(3)` 物理限；超出的 `WAITING` 排队不拒。
- **WAITING 队列 = PG**：`status='WAITING'` 记录按 `created_at` 升序，**不在 JVM 复制**。
- **派发器（`RunDispatcher`）**：单 JVM，事件驱动——`start` 创建后 + lane 释放后——各触发一次"取最旧 WAITING -> CAS 翻 RUNNING -> 提交到 RunLanePool 固定线程"。低频兜底轮询（5s）防丢事件。单实例无需 `FOR UPDATE SKIP LOCKED`（无多 JVM 消费者）。
- **CAS**：`UPDATE collection_run SET status='RUNNING', started_at=now() WHERE id=? AND status='WAITING'`，affected rows = 1 才提交到 lane；= 0 说明被别处取走（单 JVM 下不会发生，兜底）。
- **单实例**：M3 仅声明单实例 + 启动恢复；第二个实例连同一业务库的拒绝租约 M6（architecture §11）。

### D9. 单页执行引擎（`SinglePageRunExecutor`）

运行在 RunLanePool 的固定线程上，持有 `RunExecutionContext`（volatile `cancelRequested` + 计数器）：

```
1. 检查 cancel -> 新建 BrowserContext (非持久化)
2. for attempt in 1..3:
   a. 检查 cancel / elapsed > 30min
   b. page.navigate(startUrl)  等 DOMContentLoaded
      - 失败 (超时/错误) -> 记 run_event WARN, continue 重试
      - 入口连续失败到第 3 次 -> stopReason=ENTRY_FAILED, 状态 FAILED, break
   c. TargetUrlPolicy.validate(page.url())  (复用 M2 BasicTargetUrlPolicy)
      - 最终 URL 不合法 -> stopReason=ENTRY_FAILED, FAILED, break
   d. 等待字段选择器 (page.waitForSelector, 15s 超时)
      - 多匹配不阻塞 (ExtractionPreview 取第一个 + MULTIPLE_MATCH 诊断)
   e. extraWaitSeconds (0-5) 额外等待
   f. 检查 cancel
   g. 构造 DomState (从运行 lane Page) -> ExtractionPreview.preview(snapshot.definition, domState)
   h. RunResultSink.appendBatch(runId, [1 条结果], [事件])
      - 成功 -> stopReason=COMPLETED, 状态 SUCCESS, break
      - 提取异常 -> 记 run_event ERROR, continue 重试
3. 3 次全败 -> stopReason=PAGE_RETRY_EXHAUSTED, 状态 FAILED
4. 收尾: 写终态 (status/stop_reason/finished_at/计数), 关 Context, 归还 lane, 触发 RunDispatcher 派发下一个
```

- **重试语义**：单页只有 1 个逻辑页，重试 2 次（共 3 次）；全败 = `FAILED`（**不**是 `PARTIAL_SUCCESS`——单页无法"部分成功"）。任一次成功 = `SUCCESS` + 1 条结果。`PARTIAL_SUCCESS` 状态在枚举里留位，M3 代码不迁移到它（M4 多页才可达）。
- **取消检查点**：导航前、页面就绪后、提取前、终态写入前。Playwright 15s 元素等待超时兜底——即使取消信号在 `waitForSelector` 期间到达，最多 15s 后操作返回，循环下一轮即查取消。
- **取消终态**：`status=CANCELLED`, `stop_reason=USER_CANCEL`；已写结果保留（product-spec §7.4）。
- **限制检查**：每轮检查 `page_count`（200）、`record_count_final`（10000）、`elapsed`（30min）。单页下 `page_count=1`、`record_count=1`，故 `PAGE_LIMIT`/`RECORD_LIMIT` 不可达；`TIME_LIMIT` 可达（30min 上限，单页罕见但保留检查）。前向兼容，M4/M5 起作用。
- **HTTP 429/403/验证码**：单页遇 429、持续 403 或验证码 -> 退避并停止（`stopReason=HTTP_429`/`HTTP_403`/`CAPTCHA`），不切 UA/指纹/代理（product-spec §10）。M3 在导航/提取异常分类时识别。
- **进度推送**：每个阶段变更/结果写入/终态都写 `run_event` 并经 WS 推送（D16）。

### D10. 运行状态机（7 态，M3 产 6 态）

```java
public enum RunState {
    WAITING, RUNNING, SUCCESS, PARTIAL_SUCCESS, FAILED, CANCELLED, INTERRUPTED
}
```

迁移（architecture §5 状态图）：

- `[*] -> WAITING`（start 创建）
- `WAITING -> RUNNING`（派发器获得 lane）
- `WAITING -> CANCELLED`（用户取消排队中的运行）
- `WAITING -> INTERRUPTED`（启动恢复扫描）
- `RUNNING -> SUCCESS`（单页提取成功）
- `RUNNING -> FAILED`（入口失败 / 重试耗尽 / 浏览器启动失败）
- `RUNNING -> CANCELLED`（用户取消）
- `RUNNING -> INTERRUPTED`（应用退出）
- `RUNNING -> PARTIAL_SUCCESS` —— **M3 不产生**（留位 M4 多页混合成功/失败）

check constraint 含全部 7 态（D5），M4 不需要 migration 放宽。

### D11. `stopReason` 枚举（前向兼容全集）


### D13. 流式导出（CSV/JSON）

- `RunExport.writeCsv/writeJson` 直接写 `HttpServletResponse.getOutputStream()`，**不在磁盘生成临时文件**（architecture §3.6）。
- keyset 游标分页：`SELECT data FROM run_result WHERE run_id=? AND sequence_no > ? ORDER BY sequence_no LIMIT 1000`，循环直到无数据。10k 行不全量加载（roadmap §7 退出标准）。
- CSV：表头从快照字段名生成；每行按字段顺序输出 `cleanedValue`（空值输出空串）。OpenCSV 流式 `CSVWriter`。
- JSON：`[{...}, {...}]` 数组，Jackson `JsonGenerator` 流式写，每条 flush。
- 导出所有权校验同查询；admin 可导出任意 run。
- Controller：`GET /api/runs/{runId}/results/export?format=csv|json` -> `ResponseEntity<StreamingResponseBody>` 或直接 `HttpServletResponse`。

### D14. 保留清理（`RetentionCleanup`）

```java
@Component
public class RetentionCleanupTask {
    @Scheduled(cron = "0 17 3 * * *")  // 每日 03:17
    public void run() {
        int deleted = retentionCleanup.deleteExpired(clock.instant());
        LOG.info("retention cleanup deleted {} runs", deleted);
    }
}
```

- `deleteExpired`：`DELETE FROM collection_run WHERE finished_at < now() - '30 days'::interval`，FK `ON DELETE CASCADE` 级联删 `run_result` / `run_event`（不在 Java 逐行删，architecture §6.3）。
- 30 天 M3 写死常量 `RETENTION_DAYS = 30`；`system_setting` 可配延后 M6（与 ADR-0004 同先例）。
- 不删 `collection_task`（任务长期保留，product-spec §8）。
- `@EnableScheduling` 在 `Application` 启用；`Clock` 注入便于测试。

### D15. 中断恢复（`RunRecovery`）

```java
@Component
public class RunRecovery implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        int n = jdbc.update(
            "UPDATE collection_run SET status='INTERRUPTED', stop_reason='APP_INTERRUPTED', " +
            "finished_at=now() WHERE status IN ('WAITING','RUNNING')", Map.of());
        LOG.info("run recovery: marked {} leftover runs INTERRUPTED", n);
    }
}
```

- 启动时一条 `UPDATE`，不续跑（product-spec §7.4）。
- 已持久化结果仍可查询/导出（roadmap §7 退出标准）。
- 在 `RunLanePool` 初始化之后、`RunDispatcher` 接受新 run 之前执行（顺序：恢复扫描 -> 池就绪 -> 派发器启动）。

### D16. 进度 WebSocket（`/ws/runs/{runId}`）

- 端点：`/ws/runs/{runId}`，在 `WebSocketConfig` 注册（与 `/ws/visual-sessions/{sessionId}` 并列）。
- 握手：`RunOwnerHandshakeInterceptor`（镜像 `SessionOwnerHandshakeInterceptor`）——JSESSIONID 已登录 + `runId` 来自 path + run 存在 + **owner 等于 actor 或 actor 是 admin**（admin 可访问任意 run，product-spec §4.1；与配置会话不同，配置会话 admin 不可接管）+ CSRF（XSRF-TOKEN cookie vs `csrfToken` query）+ same-origin。
- 服务端 -> 客户端消息（JSON，含 `schemaVersion: 1`）：
  - `{type: PROGRESS, status, stage, currentUrl, pageCount, recordCountRaw, recordCountFinal, failCount, elapsedMs}` —— 状态/批次边界推送；单页 M3 约 5–6 条。
  - `{type: EVENT, level, stage, url, errorCode, message, createdAt}` —— 新 `run_event` 时推送。
  - `{type: TERMINAL, status, stopReason, finishedAt}` —— 终态。
- 客户端 -> 服务端：仅 `{type: CANCEL}`（重校 run 所有权，等价 `POST /api/runs/{runId}/cancel`）。
- 推送节流：单页不会溢出；M4/M5 多页时若 >10 msg/s 合并 `PROGRESS`（保留最新）。帧通道不传画面。
- 握手后先下发一次 `progress()` 快照（当前状态），再续推送增量。
- WS 会话随运行终态后由服务端关闭（发完 `TERMINAL` 后 close）。

`scripts/e2e/m3-smoke.ps1` / `m3-smoke.sh`（前提：M2 smoke 全绿）：

1. 启动 JAR + fixture HTTP server。
2. collector 登录 -> 建单页任务 -> 配置至 READY（复用 M2 路径或直接构造 READY 定义）。
3. `POST /api/runs` -> 202 `{runId, WAITING}`。
4. WS 连接 `/ws/runs/{runId}`（带 CSRF）-> 收到 PROGRESS。
5. 运行推进 -> 收到 TERMINAL {status: SUCCESS}。
6. `GET /api/runs/{runId}/results` -> 1 条结果。
7. `GET /api/runs/{runId}/results/export?format=csv` -> 下载 1 行 CSV。
8. `GET /api/runs/{runId}/snapshot` -> 固化定义。
9. 第 2 个 run（同用户，第 1 个未终态时）-> `USER_RUN_LIMIT`。
10. cancel 路径：start -> `POST /cancel` -> CANCELLED + lane 释放。
11. 强制停止 JAR -> 重启 -> `GET /api/runs` 遗留运行 INTERRUPTED + 已写结果可导出。
12. admin 登录 -> 能看到 collector 的 run + 导出。
13. `pwsh` 验证 0 个 ms-playwright / driver 残留。

Linux smoke 受 M0 决策门约束（M7 才补真机），spec 写明 `Linux smoke: not executed in M3; see M7`。

### T5. 10k 流式导出专项

- fixture：直接向 `run_result` 插入 10,000 行（绕过运行引擎）。
- `RunExportIT` CSV/JSON 各跑一次：断言行数=10000、首行字段名、末行数据；JVM 堆不爆（`-Xmx` 受限下通过）。
- 断言 fetch 批次 ~1000（通过 spy `JdbcRunResultRepository` 计数 `SELECT` 次数）。

### T6. 优先级与价值

按 architecture §9：

- T1（模块接口）-> 廉价快速、覆盖状态机/重试/取消/导出/清理矩阵，先做。
- T2（PG IT）-> 真实依赖、覆盖并发/快照不变性/级联/恢复。
- T3（Playwright IT）-> 真实 Chromium 行为差异（导航超时、重试、取消释放）。
- T4（E2E smoke）-> 覆盖 acceptance 退出标准。
- T5（10k 导出）-> 验证流式不 OOM。

`@Disabled` 仅允许 M0 spike 已存在的 `ScreencastFrameProducerIT`；M3 不新增任何 `@Disabled`。

## Out of Scope

- 列表模式 (`mode=LIST`) / 列表项推断 / 翻页 / 加载更多 / 内容页 -- M4/M5。
- 运行内去重（`unique_key_hash` M3 恒 NULL，列已占位）-- M4。
- 同域名并发 1 + ≥1s 请求间隔限速 -- M5（M3 单页 1 次导航，不涉及）。
- `PARTIAL_SUCCESS` 状态产生逻辑 -- M4（枚举已建，M3 不迁移到它）。
- `PAGE_LIMIT` / `RECORD_LIMIT` 实际触发 -- M4/M5（检查已写，单页不可达）。
- 完整 SSRF 校验（IPv4/IPv6 解析、私有/回环/保留/云元数据、DNS 重绑定、`page.route()` 子资源拦截）-- M6（M3 复用 `BasicTargetUrlPolicy`）。
- 配置化容量/保留（`system_setting` 写入）-- M6（M3 全常量）。
- 第二实例拒绝租约 / 数据库锁 -- M6（M3 仅声明单实例 + 启动恢复）。
- 定时调度 / 通知 / 跨运行增量 / 断点续跑 -- 首版后候选。
- 跨平台 Linux 实机 smoke / 真机 LAN 延迟 -- M7。
- HTTPS / Secure Cookie / 公网部署 -- 产品 §11 已声明不做。
- Testcontainers / Docker / Redis / Nginx / MQ -- AGENTS 已声明不引入。
- 运行实时画面直播 -- 产品 §7.5 已声明不做（M3 仅进度推送）。
- i18n / 英文错误消息 -- M7。

## Further Notes

- **M2 -> M3 的契约**：`ExtractionPreview`（D7 类型感知后）是预览与运行共用接口；`TaskSnapshotFactory` M1 占位 -> M3 接实现；`TargetUrlPolicy` M3 运行入口复用，M6 替换完整 SSRF；`ConfigLanePool` 不变，`RunLanePool` 同构新建（ADR-0004）。
- **M3 -> M4 的契约**：`RunState` 7 态、`StopReason` 全集、`run_result.unique_key_hash` 列、`RunResultSink` 批量接口、`RunLanePool`/`RunDispatcher` 多页循环扩展点——M4 加列表/去重/多页时不改 schema、不迁移、不破接口（"宽接口窄实现"）。
- **M3 -> M6 的契约**：容量/保留常量 M6 入 `system_setting`；`BasicTargetUrlPolicy` M6 替换完整 SSRF；`RunRecovery` M6 叠加单实例租约；调用点不变。
- **与 ADR-0006**：本 spec §D8 是该 ADR 的实施落地；任何 M3 代码违反 ADR-0006 时由 PR review 阻断。
- **诚实标注**：M3 spec 在 Linux smoke 段写明「Linux smoke: not executed in M3; see M7」；同域名限速、去重、`PARTIAL_SUCCESS` 标明 M4/M5，符合 AGENTS "不能静默跳过后宣称全部通过"。
- **与 roadmap §7 退出标准**：7 条退出标准由 issue (g) `m3-smoke.ps1` + 各 IT 一一对应：① 单页 run -> 快照/运行/1 结果 -> `SinglePageRunIT` + smoke step 5-6；② 编辑原任务不动快照 -> `RunCoordinatorIT`；③ 超时重试 + 取消释放 -> `RunRetryIT` + `RunCancelIT`；④ 强制退出重启 -> INTERRUPTED + 可导出 -> `RunRecoveryIT` + smoke step 11；⑤ 10k CSV/JSON 流式 -> `RunExportIT` + T5；⑥ 不能读他人结果 -> `RunResultQueryIT` + smoke step 12；⑦ 到期清理级联不删 task -> `RetentionCleanupIT`。
- **XPath 修复的归属**：`DomState` 类型感知是 M2 潜伏隐患的修复，随 (a) 落地而非单开 M2 修复 issue——因为 M2 退出标准未覆盖 XPath-in-preview，且 M3 运行才真正强制要求 honor XPath 选择器。PR 描述需点明"顺带修 M2 隐患"。
- **单页与状态机的边界**：`PARTIAL_SUCCESS` 是这套机器里最典型的"为 M4 建但 M3 不到"的状态。把它写进 check constraint 而非代码迁移目标，是"宽接口窄实现"原则的具体体现；M3 review 时任何把单页 run 标 `PARTIAL_SUCCESS` 的代码都是错的。
