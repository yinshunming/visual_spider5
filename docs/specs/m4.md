## 上游约束（M3 已落地的契约与 seam）

M3 已经为 M4 做了完整的前向兼容落地，M4 不重写、不迁移、不破接口：

- `RunState.PARTIAL_SUCCESS` — M3 schema 留位，M4 首次产生
- `StopReason.{PAGE_LIMIT, RECORD_LIMIT, TIME_LIMIT}` — M3 枚举留位，M4 首次可达
- `run_result.unique_key_hash` — 列已占位，M3 恒 NULL，M4 启用
- `RunResultSink.appendBatch(runId, results, events)` — 批量接口已有，M4 一次追加多条 list-item 结果
- `RunLimits.{MAX_PAGES=200, MAX_RECORDS=10000, MAX_DURATION=30min}` — 常量已就绪，M4 才真有触发路径
- `ExtractionPreview` / `DomState.query(selector, SelectorType)` — M3 加的类型感知，预览与运行共用同一解析器（修 M2 XPath 隐患的回退路径已收尾）
- `WaitPolicy(extraWaitSeconds 0–5)` — M3 加，M4 直接复用
- `TaskDefinition.schemaVersion` 当前为 1；M4 bump 到 2
- `CollectionRun.snapshot` JSONB 不可变，M4 运行仍只读已固化快照
- REST + WS `/api/runs/**` / `/ws/runs/{runId}` — M3-5 已产品化，M4 升级不是新建

## Problem Statement

M3 让单页任务真正能跑出结果；list 字段 UI（M2-3）能保存，但在配置侧：

- 没有"代表项 → 候选列表项规则"的推断算法；
- 没有相对列表项的字段预览；
- 没有"最多 20 条结果记录"的有界预览；
- 没有 list 模式下的 `READY` 规则校验；
- 没有 list 模式运行的执行引擎、计数（raw/dedup/final/fail）与 `PARTIAL_SUCCESS` 触发逻辑；
- 没有运行内 `unique_key_hash` 去重。

M4 要在不引入翻页/内容页/无限滚动/多级结构的前提下，把"当前列表页能列出多条扁平结果并去重"这条纵向切片打通。如果不把 M4 的边界澄清，会同时出现：

- **跨里程碑堆叠**：list-item 多选择器与 M5 翻页 / 内容页 URL 规则混在一起，提前把 `paginationRule` / `contentPageLinkRule` 字段加进 TaskDefinition，违反 roadmap §8 不做项。
- **schema 演进失控**：在 V2 加 `listItemRule`/`uniqueKey`/`limits` 时如果不 bump `schemaVersion`，runtime reader 与历史 V1 任务的边界模糊，无法保证「历史 M3 任务能否读、能否起 run」的契约。
- **去重语义模糊**：如果去重放全写后端再处理，则 `raw_count`/`final_count` 的语义与 10k 上限（按哪种 count 算）边界不清；如果批次内去重而不跨批次，又会出现同一运行内重复 key 漏判。
- **多匹配放任**：list-item 下字段匹配到多个元素时若仅"取第一个 + WARN"，则同一字段在不同 list-item 上语义不稳定，可能导致结果偏差且不可解释。

## Solution

M4 落地 7 张 issue，按依赖顺序推进（a → b → c → (d ∥ e) → f → g）：

- **(a) TaskDefinition V2 形状 + V3 migration + 启动 hook 静默升 V2**：
  - `TaskDefinition.schemaVersion` 升至 2；三块新可选字段 `listItemRule` / `uniqueKey` / `limits`。
  - V3 migration：新增索引 `idx_collection_run_counters`（可选，便于 PARTIAL_SUCCESS 报告）；主活是 collection_task.definition 的字段补齐。
  - 启动 `TaskSchemaUpgrader` (ApplicationRunner) 扫描 `schemaVersion=1` 任务，按 mode 按需补字段；written back 的 JSONB 标 `schemaVersion=2`。
  - 读取路径永远先 upgrader 一次（双层防护）；writer 路径总是写 V2。
  - `TaskReadiness.validate` 升级支持 V2 校验。
  - Acceptance：迁移后仓库内全部 `collection_task.definition` schemaVersion=2；V1 任务加载后可读、可调起 preview。

- **(b) 候选推断算法 + 候选规则生成**：
  - `CandidateListItemInferrer`：输入 clicked element，给出 `ListItemRule` 候选 + 评分。
  - 算法：DOM 层级（向上逐 ancestor）+ 启发式评分（sibling 数、子结构相似度、文本 token 一致性）。
  - `ListItemRuleAdjuster`：UI/后端共同调用的 ancestor 上下调整接口；任何调整都重新跑相对字段匹配。
  - `ListItemRuleValidator`：与 M2 selector 校验共用同一段一致性逻辑。
  - Acceptance：标准列表 / 卡片网格 / 嵌套列表 fixture 都能给出可解释候选；ancestor 调整可上下移动。

- **(c) 相对字段规则 + 列表预览 20 条**：
  - 字段规则从「绝对 DOM」改为「相对 list-item root」；M2 `FieldDefinition` 字段从 DOM 上下文为 list-item 内部查询。
  - `ExtractionPreview.preview` 接 listItemRoot + per-item preview 预算（M4 上限 20 条 / M3 单页 1 条 / SPEC 8.3 内容页仅 3 条 = preview 边界：当前 list 模式上限 20）。
  - 多匹配策略升级：`list-item` 下任一字段选择器匹配到 >1 个元素 → 阻止 READY + 明确 `MULTIPLE_MATCH` 诊断（D7）。
  - 系统/手写 selector 一致性：preview 与 run 共用同一相对解析器。
  - Acceptance：list-item 字段预览取到值；20 条上限生效；多匹配任务不被放行 READY。

- **(d) `RunResultSink` 实时去重 + counts 字段（raw / dedup / final / fail）**：
  - `appendBatch` 增加 per-batch 去重：`unique_key_hash` 计算走 SHA-256(field_values concatenated)；批次内先看 (run_id, unique_key_hash) UNIQUE 是否冲突，冲突 → 计入 `record_count_dedup`、不写新行。
  - 新增局部索引：`UNIQUE (run_id, unique_key_hash) WHERE unique_key_hash IS NOT NULL`。
  - `appendBatch` 返回 `BatchOutcome(raw, dedup, inserted, failed)`。
  - DDL/索引进 V3 migration 同批。
  - Acceptance：同一 unique_key 第二次进 → 仅一次落盘 + 计数正确；非 unique_key 行不受影响。

- **(e) list 执行循环 + 限制检查 + PARTIAL_SUCCESS 触发**：
  - `SinglePageRunExecutor` 升级为 `ListRunExecutor`：导航 → 等待 list-item 出现 → 对每个 item 调用 `ExtractionPreview.preview` → 写 batch（sink 实时去重）→ 计数累加。
  - 限制检查每轮：`page_count` (200) / `record_count_final` (10 000) / `elapsed` (30 min)；任一达限 → `stopReason=PAGE_LIMIT/RECORD_LIMIT/TIME_LIMIT`。
  - PARTIAL_SUCCESS 触发：`final_count > 0` && `fail_count > 0` → `PARTIAL_SUCCESS`；`final_count == 0` && `fail_count > 0` → `FAILED`；全成功 → `SUCCESS`。
  - 复用 M3 retry / cancel / 30min / 200-page 检查点；M3 `SinglePageRunIT` 保留。
  - Acceptance：3 个 list fixture 跑出多结果 + 三计数正确 + PARTIAL_SUCCESS 路径触发。

- **(f) 进度 WS / REST 升级 + 前端 list UI**：
  - `/ws/runs/{runId}` `PROGRESS` 消息结构加 `listItemCount`（可空，当次 batch 命中数）；事件流加 `LIST_ITEM_SKIPPED`（如需要），与 M3 `WARN/ERROR` 框架对齐。
  - `/api/runs/{runId}` 返回三计数；`RunSummary.list` 也返回 `recordCountRaw/Dedup/Final/Fail`。
  - 前端 `VisualSessionView`：在选择模式下点代表项 → 调 `inferCandidates` → 高亮 + 数量 + ancestor 调整器 + 相对字段 UI + 20 条预览面板。
  - `TaskEditView`：list-mode 任务新增 `listItemRule` / `uniqueKey` / `limits` 编辑入口；就绪校验提示（含 MULTIPLE_MATCH）。
  - Acceptance：list 任务配置到 READY → 启动 → list 详情三计数正确。

- **(g) E2E smoke + 多形态 fixture**：
  - `scripts/e2e/m4-smoke.ps1` / `m4-smoke.sh`：建 list 任务（标准列表）→ READY → 启动 → 三计数正确 → CSV 导出多行。
  - fixture：`list/standard-list.html` / `list/card-grid.html` / `list/nested-list.html`，每形态独立 Chromium 集成测试。
  - Acceptance：3 个 fixture 全绿；Linux 标注 `not executed in M4; see M7`。

`(a)` 是契约与 schema（跨 task/extraction，seam = `TaskDefinition` / migration）；`(b)` 候选是 `extraction` 模块新接口；`(c)` 列表预览升级 `extraction`；`(d)` 去重在 `result` 模块新加批处理；`(e)` 是 `run` 模块的核心循环升级；`(f)` 是 `run` + `result` + 前端 UI 升级。

M4 不引入 Docker / Redis / Testcontainers / 任何新外部依赖；不实现下一页、加载更多、内容页、无限滚动、多级结构、跨运行增量、完整 SSRF、定时调度。

## User Stories

1. As a **首版采集人员**，I want **在 LIST 模式下点击代表项就让系统帮我识别整组重复项**，so that **我不需要手写 CSS/XPath 也能完成 list 任务配置**。
2. As a **首版采集人员**，I want **系统候选不够准时能向上/向下调整列表项范围**，so that **工具帮我起头但我保留决定权**。
3. As a **首版采集人员**，I want **字段定义自动相对于列表项，而不是整页 DOM**，so that **同一字段规则对每条 list-item 都一致取到正确值**。
4. As a **首版采集人员**，I want **list 预览最多 20 条记录并显示匹配数和缺失诊断**，so that **配置期间不会让服务卡死或返回大数组**。
5. As a **首版采集人员**，I want **list 运行生成多条扁平结果**，so that **一次运行覆盖整个当前页的列表**。
6. As a **首版采集人员**，I want **用 1 个或多个字段做唯一键去重，空唯一键不参与判重**，so that **重复数据不被重复记录且不会把空值当成冲突**。
7. As a **首版采集人员**，I want **运行详情显示 raw / dedup / final / fail 四个数**，so that **我能区分「抓到多少」「重复多少」「最终多少」「失败多少」**。
8. As a **首版采集人员**，I want **list 任务达到 page / record / duration 任一上限时按明确 stopReason 停止**，so that **不会跑超时也不丢原因**。
9. As a **首版采集人员**，I want **list-item 字段规则匹配多元素时阻止 READY 并明确诊断**，so that **我能在保存前修正选择器，不得到运行时才发现错位**。
10. As a **M5 接手人**，I want **M4 的 `listItemRule` / `uniqueKey` / `limits` 结构与 M3 的 batch 接口、PARTIAL_SUCCESS 触发点对齐**，so that **M5 加翻页 / 内容页时不破契约**。
11. As a **M6 接手人**，I want **M4 把 200 / 10 000 / 30min 限制都走 `RunLimits` 常量并允许 TaskDefinition 覆盖**，so that **M6 仅改常量读取路径即可入 `system_setting`**。
12. As a **首版审计员**，I want **M4 的 `run_event.message` 仍不复制堆栈，结果字段值仍不进技术日志**，so that **M1/M2/M3 的脱敏规则继续覆盖 list 路径**。

## Implementation Decisions

### D1. `TaskDefinition` 升级到 V2

```java
public record TaskDefinition(
        int schemaVersion,         // bump 1 -> 2
        TaskMode mode,             // SINGLE_PAGE / LIST
        String startUrl,
        Viewport viewport,
        WaitPolicy waitPolicy,     // M3 加, 可选
        Limits limits,             // M4 加, 可选 -> 全局默认
        ListItemRule listItemRule, // M4 加, LIST 模式必填
        List<UniqueKeyField> uniqueKey, // M4 加, 可空 -> 不去重
        List<FieldDefinition> fields) {

    public TaskDefinition {
        if (fields == null) fields = List.of();
        if (waitPolicy == null) waitPolicy = new WaitPolicy(0);
        if (limits == null) limits = Limits.globalDefault();
    }
}

public record Limits(int pageLimit, int recordLimit, Duration durationLimit) {
    public static Limits globalDefault() {
        return new Limits(RunLimits.MAX_PAGES, RunLimits.MAX_RECORDS, RunLimits.MAX_DURATION);
    }
    public Limits {
        if (pageLimit <= 0 || pageLimit > RunLimits.MAX_PAGES)
            throw new IllegalArgumentException("pageLimit 须 1.." + RunLimits.MAX_PAGES);
        if (recordLimit <= 0 || recordLimit > RunLimits.MAX_RECORDS)
            throw new IllegalArgumentException("recordLimit 须 1.." + RunLimits.MAX_RECORDS);
        if (durationLimit == null || durationLimit.isNegative() || durationLimit.compareTo(RunLimits.MAX_DURATION) > 0)
            throw new IllegalArgumentException("durationLimit 须 0.." + RunLimits.MAX_DURATION);
    }
}

public record ListItemRule(String selector, SelectorType selectorType) {
    public ListItemRule {
        if (selector == null || selector.isBlank())
            throw new IllegalArgumentException("listItemRule.selector 不能为空");
        if (selectorType == null) selectorType = SelectorType.CSS;
    }
}

public record UniqueKeyField(String fieldName) {}
```

- `schemaVersion=1` 任务通过 `TaskSchemaUpgrader` 升级（V3 migration 启动 hook）：SINGLE_PAGE 仅补 `limits`；LIST 任务缺少 `listItemRule` 时降为 DRAFT（因 V1 时期 LIST 任务没有规则，已是非可运行状态，安全降级）。
- 仅追加字段；`@JsonIgnoreProperties(ignoreUnknown = true)` 已存在 → V1 反序列化到 V2 reader 不炸。
- **bump `schemaVersion=2`**：识别 TaskDefinition 形状变更（listItemRule 影响 extraction、uniqueKey 影响 result）。

### D3. `CandidateListItemInferrer` 算法细节

```java
public interface CandidateListItemInferrer {
    /** 输入 clicked element 信息 (含 tag/parent 链/属性/innerText 摘要), 输出候选 ListItemRule + 评分 + 候选 ancestor 路径。 */
    InferredCandidateListItem infer(DomSnapshot clicked);

    /** 沿祖先上下调整一级并重新评估 (UI 调)。 */
    InferredCandidateListItem adjustAncestor(DomSnapshot clicked, AdjustmentDirection dir);
}

public record InferredCandidateListItem(
    ListItemRule rule,
    int matchCount,
    double score,
    List<AncestorHop> ancestorPath,   // 上溯路径, 可正可逆调整
    List<CandidateScoreComponent> components,
    List<ListItemRule> alternatives) {}   // 并列分差 < 0.05 的前 3 替代候选
```

**算法步骤**（运行在 Playwright lane 上，DOM 上下文）：

1. 收集 clicked element 的祖先链（含自身），长度 ≤ 10 层（{@code MAX_ANCESTOR_DEPTH=10}，与 JS 端 {@code elementFromPoint + walk 10} 对齐）。
2. 对每层 ancestor（depth ≥ 1，自身不计），视为候选"**容器**"；统计其直接子元素，按 `(tag, firstClass)` 分组，取数量最多的<b>多数派</b>视为"列表项"。多数派 count = `matchCount`（容器内列表项数）。
3. 评分维度（4 项加权和；原 spec 权重不变）：

| 维度 | 权重 | 公式 | 描述 |
| --- | --- | --- | --- |
| siblingCount | 0.4 | `min(matchCount, 5) / 5.0` | 多数派子元素数（饱和 5） |
| structureSimilarity | 0.3 | 多数派两两 structureKey jaccard | structureKey 含 `{tag, class, attrs, child:{tag}:{count}}` |
| textSimilarity | 0.2 | 多数派两两 textTokens jaccard | innerText 头部 token 集合 |
| depthDistance | 0.1 | `1 / (1 + depth)` | 距 clicked 越近越好 |

4. 选最高分（≥阈值 0.6），生成 `ListItemRule{ selector = 多数派.tag + 多数派.firstClass, SelectorType = CSS }`。`selector` 指向列表项，与 `ListRunExecutor` / `ExtractionPreviewImpl` 的 `dom.query(listItemRule.selector())` 语义一致（选出 N 个 item，而非 1 个容器）。
5. `adjustAncestor(dir)`：方向感知找下一候选容器。UP = `depth > current` 中最小者；DOWN = `depth < current` 中最大者；该方向无候选时返回 `InferredCandidateListItem{ lowConfidence = true }`。**注**：步骤 5 字面"重跑 2–4"含阈值过滤，但 `adjustAncestor` 是用户驱动的方向调整，应允许探索低分候选（用户主动 UP/DOWN 时不应被阈值阻挡），故不应用 ≥ 0.6 阈值；目标候选的实际 score 由 `components` 暴露给 UI 判断。阈值仅作用于 `infer` 的初始自动选择。

**关键设计要点**：

- **评分对象 = 容器**（不是 clicked 本身），最终 `selector` = 容器的多数派子元素（列表项）。
- **`structureKey` 包含子元素 tag 计数**（`ElementSignature.childTagCounts: Map<tag, Integer>`）：让"子结构一致"的容器（如 `<tbody>` 的 5 个 `<tr>`，每个含 3 个 `<td>`）得 `structRaw=1`；"子结构各异"的容器（如 `<tr>` 的 3 个 `<td>`，分别含 `<a>`/`<span>`/文本）得 `structRaw ≈ 0`，避免"单元格相似的行"骗过算法。
- **fake fixture 须建模真实 DOM 变化**：每个 item 的字段子元素各异、各 item 文本不同。原 fake 用了全 identical 签名，会让 broken 算法骗过单元测试（re-baseline 阶段1发现的盲区）。

实测：standard-list → `tr`（5）、card-grid → `div.card`（6）、nested-list → `li.item`（4/6）；3 个 fixture 在真实 Chromium + `ListCandidiateInferenceIT`（spec §T3）端到端验证通过。

输入/输出：

- 候选 ≤ 2 时提示"页面缺乏重复结构"。
- 多候选（并列分差 < 0.05）展示前 3 个让用户挑（仅 UI）。
- fixture 评估：标准表格 / 卡片网格 / 嵌套列表各给 ≥1 个有效候选。

### D5. `UniqueKey` 与 NULL 语义

```java
public record UniqueKeyField(String fieldName) { ... }

// 计算: SHA-256(canonical_json([fieldName -> finalValue, ...] of one result))
// 任意 fieldName 对应 finalValue 为 null/空 -> 整个 hash 记为 NULL (不参与去重)
// 全部 field -> NULL: 该 record 既不判重也不去重 (保留)
```

实现:

```java
public final class UniqueKeyHasher {
    public static byte[] hash(List<UniqueKeyField> keys, Map<String, String> finalValues) {
        var presentKeys = keys.stream()
            .filter(k -> finalValues.get(k.fieldName()) != null && !finalValues.get(k.fieldName()).isBlank())
            .toList();
        if (presentKeys.isEmpty()) return null;
        var canonical = presentKeys.stream()
            .map(k -> new AbstractMap.SimpleEntry<>(k.fieldName(), finalValues.get(k.fieldName())))
            .sorted(Map.Entry.comparingByKey())
            .collect(Collectors.toList());
        var json = canonicalJson(canonical);  // 稳定序列化
        return MessageDigest.getInstance("SHA-256").digest(json.getBytes(StandardCharsets.UTF_8));
    }
}
```

- 全部空键 → `unique_key_hash IS NULL`；该 record `record_count_dedup` 不计入。
- 部分空键 → 该 record 当作 unique_key_hash=NULL（不参与本批次判重）。
- 同 key 在不同 record 上 → 第二次进批次：先 `SELECT ... WHERE run_id=? AND unique_key_hash=?` → 命中 → 计入 `dedup` 不写。

### D6. `RunResultSink.appendBatch` 实时去重

```java
public record BatchOutcome(int rawCount, int dedupCount, int insertedCount, int failedCount) {}

public interface RunResultSink {

                             List<ResultRecord> results,
```

实现 `JdbcRunResultSink`：

```java
@Transactional
public BatchOutcome appendBatch(long runId, List<ResultRecord> results, List<RunEventInput> events) {
    int inserted = 0, dedup = 0, failed = 0;
    for (var r : results) {
        try {
            byte[] hash = UniqueKeyHasher.hash(r.uniqueKey(), r.finalValues());
            if (hash == null) {
                insertRaw(runId, r, null);
                inserted++;
                continue;
            }
            if (existsByKey(runId, hash)) {
                dedup++;
                continue;
            }
            insertRaw(runId, r, hash);  // 局部唯一索引兜底 (并发)
            inserted++;
        } catch (DataIntegrityViolationException dup) {
            dedup++;  // 并发兜底
        } catch (Exception ex) {
            failed++;
            events.add(RunEventInput.error("RESULT_SINK", null, "RESULT_WRITE_FAILED", ex.getMessage()));
        }
    }
    // 事件批量插
    insertEvents(runId, events);
    // collection_run 计数累加
    jdbc.update("""
        UPDATE collection_run
        SET record_count_raw = record_count_raw + ?,
            record_count_dedup = record_count_dedup + ?,
            record_count_final = record_count_final + ?,
            fail_count = fail_count + ?
        WHERE id = ?
        """, rawSize, dedup, inserted, failed, runId);
    return new BatchOutcome(results.size(), dedup, inserted, failed);
}
```

- 局部唯一索引 `uq_run_result_dedup_key (run_id, unique_key_hash) WHERE unique_key_hash IS NOT NULL` 兜底并发（单 JVM 派发器也加，避免 `page_count` 多轮同 key 漏判）。
- `record_count_raw = record_count_raw + batchResults.size()` 是"原始进 sink 数"；`record_count_dedup` 是重复跳过；`record_count_final` 是新写入（= `final_count`）；`fail_count` 是 sink 写入失败。
- 终态报告：`RunStats` = {raw, dedup, final, fail} 来自 `collection_run.*_count`。
- 限制检查 `final_count ≥ recordLimit` → stopReason=RECORD_LIMIT。

### D8. `ListRunExecutor`（与 `SinglePageRunExecutor` 同骨架）

```java
final class ListRunExecutor implements RunExecutor {
    // 2 参 RunExecutor SPI（execute(context, runId)），内部自取 snapshot，镜像 SinglePageRunExecutor。
    // 原 spec 此处写 execute(runId, snapshot, ctx) 3 参属设想接口；M3 实际 RunExecutor SPI 为 2 参，M4 以代码为准。
    public void execute(RunExecutionContext ctx, long runId) {
        TaskSnapshot snap = repository.findById(runId).snapshot();
        try (ctx) {
            var page = openPage(snap.definition().startUrl());
            page.waitForLoadState(LoadState.DOMContentLoaded);
            TargetUrlPolicy.validate(page.url(), snap.definition().startUrl());

            // 等待 listItemRule 选择器首次出现 (15s)
            page.waitForSelector(snap.definition().listItemRule().selector(), new WaitOptions().timeout(15s));
            if (snap.definition().waitPolicy().extraWaitSeconds() > 0) sleep(snap.definition().waitPolicy().extraWaitSeconds() * 1000);

            var listItems = page.querySelectorAll(snap.definition().listItemRule().selector(), snap.definition().listItemRule().selectorType());
            var batch = new ArrayList<ResultRecord>();
            var events = new ArrayList<RunEventInput>();
            int pageCount = 0;

            for (ElementHandle item : listItems) {
                if (ctx.isCancelRequested() || isOverLimits(ctx)) break;
                pageCount++;
                // 每 item: 构造 DomState -> ExtractionPreview.preview(singleItem) -> 单条 ResultRecord
                var singleResult = previewSingleItem(item, snap);
                if (singleResult.ok()) {
                    batch.add(singleResult.toRecord(snap.definition().uniqueKey()));
                    events.add(RunEventInput.info("LIST_ITEM_EXTRACTED", item.url(), null, "extract ok"));
                } else {
                    events.add(RunEventInput.warn("LIST_ITEM_FAILED", item.url(),
                            singleResult.errorCode(), singleResult.message()));
                }
                if (batch.size() >= 100) {  // 批大小: 经验值
                    sink.appendBatch(runId, batch, events);
                    batch.clear(); events.clear();
                }
            }
            if (!batch.isEmpty()) sink.appendBatch(runId, batch, events);

            // 终态: PARTIAL_SUCCESS / SUCCESS / FAILED per D7
            repo.terminal(runId, computeState(runId), computeStopReason(runId), now());
        } catch (Exception ex) {
            handleRunFailure(runId, ex);
        } finally {
            closeContext();
        }
    }
}
```

- 取消检查点：每 item 循环、sink.appendBatch 前后、终态写库前。
- 限制检查：`isOverLimits(ctx)` 每轮检查 page/record/elapsed；命中 → break + 落 stopReason。
- 重试：仅 list-item 失败 → 不重试（每 item 独立事件）；入口 / list-item-rule 等待失败 → 重试 2 次（共 3 次），沿用 M3 `SinglePageRunExecutor` 重试路径。
- 全部 list-item 跑过但全部失败 → FAILED + stopReason=PAGE_RETRY_EXHAUSTED（沿用 M3 习惯）。
- 同批次 batch size 100 是经验值，可调；不影响契约。
- **签名与路由（2026-08-03 re-baseline 修正）**：`ListRunExecutor implements RunExecutor`，2 参 `execute(RunExecutionContext, long runId)`，内部 `repository.findById(runId).snapshot()` 自取 snapshot（镜像 `SinglePageRunExecutor`）。原 spec §D8 写 `execute(runId, snapshot, ctx)` 3 参属设想接口，M3 实际 `RunExecutor` SPI 为 2 参，M4 以代码为准、不破 M3。模式路由见 D15。

### D14. 横切：单实例、容量、Limits 来源

### D15. dispatcher 模式路由（2026-08-03 re-baseline 新增）

M3 `RunDispatcher` 只注入一个 `RunExecutor`（`SinglePageRunExecutor`），对所有 claimed run 调 `executor.execute(context, runId)`，**无模式分发**--LIST 任务被单页执行器错跑。M4 补：

- `ListRunExecutor implements RunExecutor`（2 参，自取 snapshot，见 D8）。
- `RunDispatcher` 注入 `SinglePageRunExecutor` + `ListRunExecutor`（或 `Map<TaskMode, RunExecutor>`），`dispatchOnce` claim 后读 `rec.snapshot().definition().mode()` 选 executor 提交。
- 不引入 `RunExecutorRouter` 额外抽象（CLAUDE.md 最小改动）；M5 多页执行器直接再加一支 + 路由表扩项。
- `SinglePageRunExecutor` 行为不变（不内部分支委托），保持 M3 已验证代码不动。
